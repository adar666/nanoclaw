## Findings

### Per-story findings (already resolved within each story's own build)

Each story's own step-04 review (blind-hunter/edge-case-hunter/verification-gap) already found and routed real findings — summarized here only for epic-level context, full detail lives in each story's own Spec Change Log:

- **2-1 (OCR):** reversed two frozen "no OCR engine" decisions deliberately (pre-authorized by `epic-2-context.md` itself); step-04 found and fixed a near-empty-threshold gap, a render-cleanup-on-failure gap, added Hebrew support per operator decision.
- **2-2 (batch fill):** step-04 found and fixed a real frozen-Boundary violation — a thrown (not returned) per-target failure used to collapse the whole batch and discard already-recorded successes.
- **2-3 (version history):** step-04 found and fixed a real data-loss risk — the fill-history JSON write wasn't atomic, so a crash mid-write could silently wipe a document's entire history.
- **2-4 (auto-refresh):** the largest per-story review in the epic, matching its real risk increase (first story to mutate previously-immutable stored content). step-04 found and fixed a metadata bug (refresh was overwriting the document's original filename/description with the new source file's own machine-generated name), an unintended containment-widening bug, and a fill/refresh concurrency race.

### Spec-to-implementation reconciliation

`epic-2-context.md` flagged two cross-story dependencies before any story shipped:

1. **"Story 2.3 and 2.4 both touch the same open question [what happens to stored state after a fill]... should be scoped with awareness of each other."** Resolved coherently and explicitly — spec-2-3's own Design Notes anticipated the handoff and named it as unresolved; spec-2-4's own Design Notes directly answered it by reusing 2-3's fill-history mechanism rather than building a second, parallel one. No conflicting design landed.
2. **"Story 2.2 would call the same per-document fill logic Story 2.4 might change the post-fill behavior of — sequence-sensitive if both are picked up close together."** Resolved in outcome, but by story-ordering luck plus review discipline rather than explicit cross-story coordination — 2.2 shipped and closed strictly before 2.4 started, and when 2.4 did touch the shared `fillOneDocument`, it found a real, previously-latent concurrency bug live during its own step-04 review (fixed then; further hardened by this retro's item 3). No shipped defect, but the flagged sequence-sensitivity was genuinely real, and nothing carried the epic-level note forward as an explicit checklist item for either story — it surfaced only because 2.4 happened to be the story mutating shared state and ran a thorough review.
