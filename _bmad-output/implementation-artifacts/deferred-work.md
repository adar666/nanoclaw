- source_spec: `_bmad-output/implementation-artifacts/spec-cal-2-3-calendars-beyond-uriel-and-devorah.md`
  summary: Concurrent `ncl groups config add-calendar`/`remove-calendar` calls on the same group can lose an update (read-then-write, not transactional) — same class of race as every other `config add-X`/`remove-X` JSON-column CLI verb on this table (mounts, MCP servers, packages), not new to this story.
  evidence: Edge-case-hunter review finding; pre-existing systemic pattern across the whole `config add-X` family, surfaced incidentally by this story rather than introduced by it.
  status_check: 2026-08-19 — investigated rather than blind-patched, per user request to scope this out for real. **Not actually reachable in this codebase's current architecture, and no code change was made.** Every `config add-X`/`remove-X` handler in `src/cli/resources/groups.ts` (calendar, MCP server, package, mount — all of them, verified by reading each one) does `getContainerConfig()` → `JSON.parse()` → modify → `updateContainerConfigJson()` as one unbroken synchronous block, zero `await` between the read and the write. All `ncl` invocations — agent-initiated (`cli_request`) and human-operator-typed alike — route through the single host Node process's one Unix-socket dispatcher (`src/cli/socket-server.ts`), never a separate DB connection. JS's single-threaded execution model guarantees a synchronous function body can't be preempted mid-execution by another request's handler, no matter how the surrounding async plumbing (guard checks, approval waits) is structured — so two "concurrent" calls can only ever run fully-before or fully-after each other, never interleaved, and the described lost-update window doesn't exist. This looks like a pattern-matched false positive from the original LLM review pass (real for a naive read-then-write across an actual concurrency boundary — thread pool, separate process, or an `await` between the two steps — none of which apply here). Left as a `status_check`, not `resolved`, since nothing was fixed; re-open if this DB layer ever gains a genuine concurrency boundary (a worker pool, a second writer process) that would make the original concern real again.
