## Findings

Each story already carries its own review-loop findings and dispositions in its own Spec Change Log (`spec-cal-2-1` through `spec-cal-2-4`) and in `deferred-work.md` (15 entries added across the epic). This section covers only what those per-story passes structurally could not see: cross-story interactions and epic-wide aggregate views.

### 1. [Cross-story, FIXED] Story 2.2's `recurrence` silently defeated Story 2.1's idempotency guard for retried recurring creates

**Source:** `container/agent-runner/src/mcp-tools/calendar.ts:601` (`findDuplicateCandidate`, pre-fix), confirmed via `calendar.test.ts` — no test combined a recurring create with a recurring candidate before this retro.

Story 2.1's exclusion (`if (ev.recurrence || ev.recurringEventId) continue`) was correct in isolation: stop an unrelated pre-existing series' occurrence from false-matching a coincidentally same-titled one-off. Story 2.2 added `recurrence` as a create argument without revisiting that exclusion. Result: a retried or racing *recurring* create could never find its own just-created series as a duplicate — every real candidate carried `recurringEventId`/`recurrence` and got unconditionally skipped, so the guard reported "no duplicate" regardless of what was being created. This silently defeated AD-16's own stated guarantee for exactly the case it names as motivating it (a retried request must not silently double-book).

**Disposition: fixed now**, commit `9f03de9b`. Exclusion is now keyed on whether the *new* request is itself recurring, not on the candidate alone. Two new tests added (retry-protection case; a control case confirming recurrence never relaxes an otherwise-real match).

**Upstream lesson:** a per-story review reviews the story's own diff in isolation; an exclusion rule written to solve one story's problem can silently become wrong once a *later* story changes what "the thing being excluded" means, without the earlier code ever being touched again. Nothing in the single-story review loop process would have caught this — it's structurally a retrospective-only class of finding.

### 2. [Cross-story doc, FIXED] `ARCHITECTURE-SPINE.md` self-contradicted across the AD-2/AD-18 revision boundary

**Source:** `ARCHITECTURE-SPINE.md:6` (frontmatter `scope`), `:18` (Design Paradigm prose), `:22-27` (mermaid diagram) vs. `:43` (AD-2's own revised Rule).

AD-2's Rule bullet was correctly revised on 2026-08-18 to say the `calendar` argument "is no longer a closed two-value set." But the frontmatter `scope:` field, the Design Paradigm narrative paragraph, and the diagram all still described exactly two calendars — Story 2.3's revision touched only the one AD bullet, not the surrounding document that describes the same invariant three other ways.

**Disposition: fixed now**, commit `9f03de9b`. All three updated to reflect the registry.

**Upstream lesson:** when a spine revision changes an invariant, grep the whole document for every other place that invariant is restated (frontmatter, narrative prose, diagrams), not just the AD bullet being revised — a spine is supposed to be internally consistent by construction, and letting three restatements drift is exactly the kind of thing a spine's own self-consistency is meant to prevent.

### 4. [Spec reconciliation, OPEN] Recurring-instance `eventId` refuse-vs-allow decision, flagged before Story 2.2 shipped, never actually resolved

**Source:** `ARCHITECTURE-SPINE.md` Deferred section (pre-2.2 entry, still present) and `spec-cal-2-2-recurring-events.md`'s own AC3 flagged this explicitly: *"confirm whether `list_calendar_events` surfaces individual occurrence `eventId`s... and, if so, decide explicitly whether `update_calendar_event`/`delete_calendar_event` should refuse them."*

Confirmed via direct code read: `resolveTargetEvent` (`calendar.ts:753`) and both `updateCalendarEvent`/`deleteCalendarEvent`'s handlers have **no check** for `recurringEventId` on the resolved target. `list_calendar_events` uses `singleEvents=true` (confirmed, Story 2.1's own investigation), so it *does* return expanded instances with real, individually-addressable `eventId`s. An instance `eventId` returned by `list_calendar_events` today will silently succeed against `update_calendar_event`/`delete_calendar_event` — CAP-5's SPEC.md non-goal ("editing/cancelling a single occurrence... independently of the whole series") is true only by convention (the agent isn't instructed to do this), not structurally enforced. This is the same class of gap this project has already been bitten by once, live, in production (`delete_calendar_event`'s original `confirm: boolean` trust-the-agent design) — recorded explicitly in the spine's own Deferred section as the precedent to avoid repeating.

**Disposition: deferred, not fixed here.** This needs a real design decision (refuse instance IDs outright? allow but warn? allow silently, since Story 2.2's own spec called it "genuinely low real-world likelihood"?) — not a blind patch during a retrospective. Routed as an action item below.

**Upstream lesson:** a "before shipping X, confirm Y" note left in a Deferred section is not self-executing — nothing in the single-story build loop re-reads Deferred sections before starting the *next* story that might resolve them. If this class of note matters, it needs an explicit checklist item in the next story's own spec, not just a hope that someone remembers to look.

### 5. [Pattern, low severity] Three near-identical "hooks" testability-seam objects, never factored into a shared helper

**Source:** `calendar.ts:57` (`calendarConfigHooks`), `:1086` (`createHooks`), `:1122` (`deleteHooks`); `calendar.test.ts` `stubConfirmDeletion`/`stubConfirmCreation`/`stubCalendarRegistry` (~lines 29-76).

Structurally identical one-property-object-wrapping-a-function idiom, copy-pasted three times across Epic 1 and Epic 2. Each instance is a single line — a generic factory would be marginal, not a real duplication risk.

**Disposition: accept as-is.** Not worth the abstraction cost at this scale.

### 6. [Pattern, informational] `calendar.ts`'s testability-seam idiom diverges from `documents.ts`'s DI style, but this predates Epic 2

`calendar.ts` (Epic 1's `deleteHooks` onward) uses mutable exported hook objects tests monkey-patch; `documents.ts` uses explicit `opts.baseDir`-style parameter injection. Neither is dictated by architecture or SPEC.md. Epic 2's additions are internally consistent with `calendar.ts`'s own established convention — this is a pre-existing file-level divergence, not something Epic 2 introduced.

**Disposition: accept as-is.** Noted for a future cross-file consistency pass, not this epic's problem.

This session also surfaced and fixed 4 more real, live-only-visible bugs beyond the recurring-idempotency one already fixed in commit `9f03de9b`, none of which any test in this repo could have caught (all are deployment/infra-shaped, not code-logic-shaped):

1. **Host wasn't rebuilt** — `pnpm run build` was never run after merge, so `ncl groups config add-calendar`/`remove-calendar` (Story 2.3's own CLI surface) didn't exist on the running host process at all. Fixed: `pnpm run build` + service restart.
2. **SKILL.md caused the agent to refuse without trying** — asked about an unrecognized calendar name, the agent answered from memory ("only uriel/devorah exist") instead of calling the tool and letting it validate for real. Fixed: added an explicit "try it, don't assume" rule (commit `efd8acc1`).
3. **`dm-with-uriel` has no `people.md` of its own** — each agent group's memory is isolated; the guest-resolution instruction assumed a household-specific path that doesn't exist outside the `household` group. First patched with a manual file copy (rejected as the wrong fix — no sync mechanism), then properly fixed with a **read-only mount** of `household`'s own `people.md` into `dm-with-uriel` and `dm-with-partner` (one real file, no duplication) — `ncl groups config add-mount` + SKILL.md rewritten to name both real container paths (commit `efd8acc1`).
4. **`mount-security`'s allowlist fail-closed on the new mount** — `groups/household/memory/household/people.md` wasn't on the operator's `~/.config/nanoclaw/mount-allowlist.json`, so the mount was rejected and never reached the container. Correctly logged (`WARN "Additional mount REJECTED"`, real reason, in `logs/nanoclaw.error.log`) — diagnosed by exec'ing into the container and finding the file missing first, checking `logs/nanoclaw.error.log` only afterward, backwards from this project's own documented troubleshooting order ("host logs: `nanoclaw.error.log` first"). Fixed: added a file-level allowlist entry + service restart to reload it (operator-local config, not part of any commit). Process lesson, not a code gap: check `nanoclaw.error.log` before container-level diagnosis, every time, per the existing convention — this session skipped it once and cost a needless round trip.

All four are now confirmed working end-to-end in production. See the main session's conversation log for the full step-by-step verification and fix trail.
