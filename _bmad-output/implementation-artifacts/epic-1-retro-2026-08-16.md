## Findings

### Aggregate views

**God-class candidate — `documents.ts` (1501 lines vs. next-largest sibling `core.ts` at 244).**
Source: architecture-scan subagent, confirmed independently (`wc -l container/agent-runner/src/mcp-tools/*.ts`). Four natural split points identified, each already delimited by the file's own section banners: `pdf-extraction.ts` (text extraction + PNG rendering, lines 283–426), `docx-ooxml.ts` (OOXML tokenizer + cell-splice, 757–998), `pdf-fill.ts` (line/AcroForm/pixel overlay + Hebrew font embedding, 1000–1352, the largest and most import-heavy cluster), with the three tool definitions + shared primitives (`slugify`, `withLock`, escaping, `resolveDocument`) staying as an orchestration layer. Not a grab-bag — one real feature domain — but the domain requires several independent parsing/rendering technologies that don't share much beyond the orchestration layer. **Disposition: defer.**

**Pattern divergence — try/catch and no-DB-roundtrip vs. sibling `mcp-tools/*.ts` files.**
Source: architecture-scan subagent (grep-confirmed: zero `try {` in any other `mcp-tools/*.ts`; zero `writeMessageOut` imports in `documents.ts`). Both are explicitly intentional per the file's own header comment (`documents.ts:6-8`), not accidental drift. **Disposition: accept as-is.**

**Inconsistent `log()` usage across the epic's own 3 tools.**
Source: architecture-scan subagent. `save_document` (Story 1.1) logs on success/failure (`documents.ts:278,557`); `list_documents` and `fill_document_field` (Stories 1.2/1.3) never call `log()` at all, unlike every sibling tool which logs on essentially every invocation. **Disposition: fix now** (action item AI-1).

**Two crc32-based filename generators with opposite invariants (`renderFileNameFor` deterministic, `overlayRenderFileNameFor` unique-per-call).**
Source: architecture-scan subagent. Not a bug — the two call sites have genuinely different requirements (idempotent lookup vs. concurrency safety) — but it's the one place a "hash into a filename" pattern was written twice instead of parameterized once. **Disposition: accept as-is**, low value to unify for two call sites.

### Cross-story boundary review

Checked specifically because no single story's own review session ever saw both sides of a seam:

- **1.1 → 1.2 storage assumptions**: slug uniqueness genuinely guaranteed by construction (locked collision check, exercised by a concurrency test); frontmatter/index.md format assumptions match what 1.1 actually writes. One real gap: **`fill_document_field`'s `value` argument is never passed through `stripControlChars` before being spliced into generated OOXML** (`documents.ts:866-906` via `xmlEscapeText`, `849-851`, which only escapes `&`/`<`/`>`) — the same class of untrusted-input risk Story 1.1 explicitly guarded against for filenames (`documents.ts:220-227`'s own stated rationale), not carried over to Story 1.2's `value` input. Source: cross-story-boundary subagent. **Disposition: fix now** (action item AI-8).
- **1.2 → 1.3 boundary**: SKILL.md's documented `list_documents` behavior (candidate format, 0/1/2+ semantics, error shapes) matches the current, post-revert code exactly. The Story 1.3 revert (removing a path-suffix Story 1.3's own frozen spec had originally required) was confirmed byte-identical against Story 1.2's state (`git diff 882d796 0bf7fe6 -- documents.ts documents.test.ts` — empty) and left no stale references anywhere in code, tests, or docs. **Clean, no finding.**
- **Concurrency across all three tools**: confirmed safe by construction, not just by absence of a bug report — `fill_document_field` never writes to a shared/lockable resource (only unique-per-call output paths), and a document only becomes visible to readers after its raw file AND concept file have both landed under Story 1.1's lock. **Clean, no finding.**
- **Error-shape consistency**: all three tools return the identical `ok()`/`err()` shape via a shared top-level try/catch each; no divergent error path. **Clean, no finding.**

### Behavior verification

Passing unit tests (container: 232/232, host: 1384/1384) do not by themselves demonstrate the system works — real end-to-end checks were run against the actual functions, using inputs built by *different* tooling than the test suite's own fixtures (a real `zip`-CLI-built `.docx`, a real `pdf-lib`-built `.pdf`), to avoid the check silently validating against the same fixture-generation assumptions the tests already share:

- **docx path**: saved a real 1-table docx → `save_document` extracted "Name" + a body paragraph correctly → `fill_document_field` filled row 1's last cell with a **Hebrew value** (`עדה לאבלייס`) → the output file was independently `unzip`-inspected and confirmed byte-correct: only the target `<w:t>` run changed, `xml:space="preserve"` correctly added, rest of the document untouched.
- **PDF path**: saved a real `pdf-lib`-built single-line PDF (no form fields, no text layer initially populated as an AcroForm — pure text-layer case) → `fill_document_field`'s first call correctly returned a detected-line list → second call with a Hebrew `value` drew it correctly → the output PDF was independently reloaded via `PDFDocument.load()` and confirmed well-formed (correct page count, no corruption).

Both runs completed with zero errors and produced verifiably correct output on the epic's two riskiest/most novel code paths (real OOXML cell-splice correctness, real Hebrew glyph embedding + drawing). AcroForm-specific and scanned-PDF-specific paths were not independently re-verified beyond their unit tests in this behavior check (time-boxed to the two paths judged highest-risk); their unit test coverage (233 tests total, including dedicated AcroForm-match/no-match/non-text-field and scanned-PDF two-call tests) was not re-derived here.

**Process lesson** (the one pattern worth naming, not a one-off): three of the four spec-reconciliation gaps (AI-3, AI-4, AI-7) share a root cause — a Spec Change Log entry gets skipped when a deviation is judged self-evidently correct during a patch round, and only a code comment records it.
