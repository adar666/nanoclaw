- (decision) [ADOPTED] Paradigm: this feature is a thin vertical slice added to NanoClaw's existing layered architecture (host Node process <-> per-session Docker container via two SQLite DBs; inside the container, MCP tools exposed to the agent). No new paradigm introduced -- the feature composes onto the existing one: new MCP tool(s) in container/agent-runner/src/mcp-tools/, reusing existing inbound attachment (inbox/) and outbound file (outbox/ + send_file) plumbing, writing into the existing per-group memory/ tree.
- (version) (researched, web) pdf-lib: current npm version 1.17.1 -- PDF creation/modification incl. drawing text on an existing page (overlay write). No rendering context required. Chosen for the overlay-write half of CAP-3's PDF path (SPEC.md constraint: overlay-only, never reflow).
- (version) (researched, web) pdfjs-dist: current npm version ~6.2.108 -- Mozilla's PDF.js, used here only for text extraction WITH per-text-item positional data (transform matrix, width/height) when a PDF has a text layer. Complementary to pdf-lib, not a replacement (pdf-lib does not extract text).
- (version) (researched, web) @hyzyla/pdfium (TypeScript wrapper for PDFium): used to render a PDF page to a raster image (PNG) at a known scale factor -- needed for (a) the scanned-PDF vision-read fallback in CAP-1 and (b) the agent's visual position-estimate fallback in CAP-3's overlay path (SPEC.md row-targeting-matrix.md). Chosen over a headless-Chromium render (Puppeteer/Playwright) despite Chromium already being in the image for agent-browser, because PDFium is purpose-built and lighter -- avoids spinning up a full browser per PDF page. [ASSUMPTION: worth confirming at build time that reusing the existing Chromium (already paid for in image size) isn't preferable to adding a second rendering dependency -- flagged, not decided against.]
- (decision) [ASSUMPTION] docx (Word) table-cell editing: no single well-established, template-free 'edit an arbitrary existing docx' library surfaced in research with strong adoption. Leaning toward direct OOXML manipulation -- JSZip (well-established, already a transitive dependency pattern used by pdf-lib-adjacent tooling) to unzip the docx, edit word/document.xml's target table cell run text, rezip -- over docxtemplater (built for placeholder templates, not arbitrary existing documents) or newer/unproven single-maintainer libraries (supply-chain risk per this repo's pnpm minimumReleaseAge policy). Known risk to flag for the builder: Word fragments visible text across multiple <w:r> runs, so a naive string match on the XML can miss the target text -- run-merging/normalization logic is needed. Marked [ASSUMPTION] for review.
- (decision) [ADOPTED] New MCP tools live in a new container/agent-runner/src/mcp-tools/documents.ts, following the existing McpToolDefinition + registerTools() convention (core.ts, transcribe-audio.ts), wired via a single barrel import added to mcp-tools/index.ts (no central registry list, per existing convention).
- (decision) Execution locus: document parsing/editing runs synchronously IN-CONTAINER (Bun), inside the MCP tool call itself -- NOT via the host-side fire-and-forget pattern that transcribe-audio.ts uses. Binds CAP-1/2/3. Prevents an unneeded async round-trip (tool call -> host action -> new inbound message -> agent reacts again) for what is pure local file manipulation needing no external API/credential, unlike audio transcription. The container already has direct mounted access to inbox/, outbox/, and memory/ (all under the host-side session/group dirs bind-mounted in) so there is no filesystem reason to hop to the host.
- (decision) [ADOPTED] Dependency placement: pdf-lib, pdfjs-dist, @hyzyla/pdfium, and jszip go into container/agent-runner/package.json (baked into the shared base image via Dockerfile's bun install layer) -- not the per-group install_packages self-mod flow -- because every agent group should get this capability uniformly, matching how the existing base deps (zod, cron-parser, etc.) are placed.
- (decision) Vision-fallback boundary: any step needing visual/semantic understanding of a rendered page image (scanned-PDF content reading for CAP-1, position estimation for CAP-3's overlay path) happens in the AGENT's own multimodal turn over an image the tool provides -- the MCP tool layer itself never embeds a separate OCR/vision API call. Binds CAP-1, CAP-3. Prevents two independently-built tool functions from diverging (one calling out to a vision API redundantly, duplicating a capability the agent conversation turn already has natively).
- (decision) Saved-document storage shape: raw file copied to canonical per-group location groups/<folder>/memory/documents/files/<slug>.<ext> (independent of the ephemeral per-message inbox/ it arrived through); one OKF concept file groups/<folder>/memory/documents/<slug>.md (frontmatter: type: saved-document, description, source-filename, saved-date) holding the extracted text / summary and a relative path back to the raw file; one line appended to memory/index.md per SPEC.md CAP-1. Binds CAP-1, CAP-2. Prevents relying on inbox/ as long-term storage (it is message-scoped, not group-scoped) and prevents memory/index.md from bloating with full document text instead of just a pointer.
- (decision) list_documents MCP tool returns the structured list (slug, filename, description) read from memory/documents/*.md frontmatter; the numbered pick-list itself (SPEC.md CAP-2/CAP-3 disambiguation rule) is rendered by the agent in chat, not by the tool -- the tool supplies data, the agent supplies the numbered UI.
- (constraint) [ASSUMPTION] @hyzyla/pdfium's default render path depends on the 'sharp' package (native binding) for bitmap->PNG conversion. Bun-in-Docker compatibility of sharp's native binary for this base image is unverified -- flag for build-time confirmation; pdfium.js.org also documents a pure-bitmap render engine with no extra dependency as a fallback if sharp proves incompatible.
- (constraint) [ASSUMPTION] docx table-cell editing: no established template-free 'edit an arbitrary existing docx' library with strong adoption surfaced in research. Leaning toward direct OOXML manipulation via jszip (unzip -> edit target <w:tc> run text in word/document.xml -> rezip) over docxtemplater (template/placeholder-oriented, not arbitrary existing documents) or newer single-maintainer libraries (supply-chain risk per this repo's pnpm minimumReleaseAge policy, though that policy technically only governs the host's pnpm tree, not agent-runner's Bun tree -- still treated as the same discipline). Known risk for the builder: Word fragments visible text across multiple <w:r> runs; naive string matching on raw XML can miss the target cell's text and needs run-merging/normalization logic.
