# Review — ARCHITECTURE-SPINE.md (Cross-Group Context Sharing + Provenance/Receipts)

Reviewed: `_bmad-output/planning-artifacts/architecture/architecture-nanoclaw-v2-2026-08-31/ARCHITECTURE-SPINE.md`
Against: `_bmad-output/specs/spec-context-sharing-and-provenance/SPEC.md`, live repo source (2026-08-31)

## Verdict

Mostly sound and unusually well-verified in its factual claims (AD-3/AD-4/AD-8/AD-9/AD-10/AD-12 all check out cleanly against real source), but AD-5's mount-path convention is internally inconsistent with the codebase's own proven precedent for the identical mechanism and would not work as literally written, and AD-2's "reuse add-mount as-is" silently inherits a read-write-by-default footgun that contradicts the SPEC's explicit read-only/no-write-back constraint — both are load-bearing for CAP-1 and need a fix before this is build-ready. The Deferred section's operational-envelope claim is also factually wrong for CAP-2.

## Critical findings

1. **AD-5's mount-path convention doesn't match the codebase's own proven precedent and likely doesn't work.** AD-5 says `--container-path` must be `shared/<source-group-folder>` (no filename), and `read_shared_context` appends `/shared-facts.md` to build `/workspace/extra/shared/<source-group-folder>/shared-facts.md`. But this repo's own existing single-file mount for the identical purpose (`eval/setup.ts`'s `ensureEvalPeopleMount`, cited approvingly in CLAUDE.md's own pitfalls list) uses `containerPath = 'household-shared/people.md'` — i.e. the filename is *part of* the configured container path, because a Docker bind mount of a single host file lands as a file at exactly the given container path (confirmed via `src/container-runtime.ts:31`'s literal `-v hostPath:containerPath:ro`). Under AD-5 as written, if the operator mounts the file `memory/shared-facts.md` at `shared/<folder>`, that container path IS the file — `read_shared_context`'s appended `/shared-facts.md` resolves to a non-existent path under a file, so AD-6's "not shared with you" fires even when a real grant exists. The only way to make the literal `/workspace/extra/shared/<folder>/shared-facts.md` path resolve is to mount the *whole* `memory/` directory instead of the single file — which then exposes every other file in that group's memory tree to raw filesystem access inside the target container, directly contradicting AD-3 ("this is the only file CAP-1 ever reads or expects to be mounted") and the SPEC's constraint that a group's memory stays private by default. Either way this is broken as specified; needs `--container-path` to be `shared/<source-group-folder>/shared-facts.md` (matching the proven precedent) with `read_shared_context` reading that full path directly, no directory-append.

2. **AD-2's "reuse add-mount as-is" inherits a real-write-by-default footgun that violates the SPEC's read-only constraint.** `config add-mount`'s handler (`src/cli/resources/groups.ts:576-580`) sets `readonly: Boolean(args.ro || args.readonly)`, which defaults to `false` (writable) unless the operator explicitly passes `--ro`. `validateMount` (`src/modules/mount-security/index.ts:368-380`) then grants real read-write whenever `mount.readonly === false` AND the allowlisted root permits RW. Nothing in AD-2 requires (or even flags) that a shared-context grant must always pass `--ro`, and there is no mount-purpose tagging that would let mount-security force read-only for this specific use case. If an operator sets up the grant without remembering `--ro`, the requesting group's agent gets an ordinary writable bind mount at the shared path and can edit the source group's `shared-facts.md` directly via normal file tools — completely bypassing `read_shared_context`'s read-only tool semantics and violating the SPEC's explicit "No write-back into another group's memory" constraint and its own Constraints section ("CAP-1 is read-only and one-directional per grant"). This is exactly the class of question SPEC's own third Open Question was asking ("does fact-sharing need a lighter-weight, purpose-built verb rather than raw directory mounts?") — AD-2 answers "no, reuse as-is" without addressing why the existing verb's default-writable behavior is safe here. Needs either a mandated `--ro` in the operator runbook/skill text with enforcement (e.g. a lint/audit script, mirroring `scripts/audit-attachment-drop-risk.ts`'s existing pattern for a different footgun), or AD-2 revised to require read-only explicitly at grant time.

3. **The Deferred section's operational-envelope claim is factually wrong for CAP-2.** It states: "no host rebuild unless a CLI verb's description text changes (it doesn't, here)." But AD-8 requires editing `src/cli/resources/tasks.ts`'s `create` handler (host-side `src/**`) to actually capture and write the provenance shape into `content.provenance`, and AD-9 requires editing `src/modules/self-mod/apply.ts` (also host-side `src/**`) so every `applyX` handler appends to `self-mod-log.md`. Per this project's own CLAUDE.md pitfalls (which this spine should be internally consistent with): "A host-side TS change (`src/**`) needs `pnpm run build` + a service restart... a container rebuild does nothing for it." Both AD-8 and AD-9 are host-side code changes, not CLI description-text changes, and both need a host rebuild + restart — the opposite of what the Deferred section states. This is the exact "operational/environmental envelope" dimension the review was asked to check, and it's simply incorrect as written; a build plan following this spine literally could skip the host rebuild and ship CAP-2 non-functional.

## High findings

4. **AD-7's `requesterSessionId` may be insufficient to answer "who" for a shared/agent-shared session.** Per `docs/isolation-model.md`, `session_mode: 'agent-shared'`/`'shared'` sessions can be reached by multiple messaging groups / users converging on one session id. AD-7's shape has no per-user field (only `requesterSessionId?`), so CAP-2's "why did this happen, who triggered it" success criterion may resolve to a session shared by several people, not a specific requester, in exactly the topologies this codebase already supports. Not necessarily wrong, but AD-7 doesn't acknowledge or resolve this ambiguity, and the SPEC's success text ("trigger + requester") implies a concrete requester is expected.

5. **`self-mod-log.md` (AD-9) has no cap, unlike every other file-based log this spine cites as its own precedent.** `run-log.ts`'s task-series log and `documents.ts`'s `FillHistoryEntry` index (`FILL_HISTORY_CAP = 20`) both bound their growth; AD-9 doesn't mention any cap or rotation for `self-mod-log.md`, which is a single per-group file (not per-series like run-log) that will grow unbounded over the group's lifetime. Minor compared to 1-3, but worth a line in the spec given the spine explicitly claims to "mirror the existing task run-log pattern."

## Other observations (not blocking)

- The premise that this spine "claims zero new dependencies" doesn't literally appear in the document — its actual claim is narrower ("No new runtime, no new IPC channel, no new database table"). Verified true under the narrower reading: `read_shared_context` returns raw file content (no YAML/frontmatter parsing needed per AD-6), and CAP-2 is pure JSON/markdown-append, so no new npm dependency is actually required in either `package.json` or `container/agent-runner/package.json`.
- AD-3 (OKF frontmatter, `docs/memory.md`), AD-4 (MCP tool registration convention, `mcp-tools/index.ts`), AD-8 (`kind='task'` column + `content` JSON shape, `src/modules/scheduling/create.ts` + `db.ts`), AD-9 (`applyAddCalendar` and sibling handlers, `pending_approvals` deleted-on-resolve for every action type), AD-10 (`FillHistoryEntry`'s `kind` field + `readFillHistory`'s tolerant backward-compat normalization), and AD-12 (`eval/loader.ts`'s `SCENARIO_SETS` registration convention, `guest-resolution.scenarios.ts` precedent) all check out precisely against the real source — these are accurately ratified, not just plausible-sounding.
- CAP-1 and CAP-2 are both fully mapped to ADs with no capability left ungoverned; the Deferred section correctly closes out all three of SPEC's Open Questions (tool-vs-CLI, push-vs-pull digest, add-mount-vs-lighter-weight-verb) even though finding 2 above shows the third answer has an unaddressed gap.
- Named tech is current: no new libraries, no version claims to verify beyond what's already in `package.json`/`container/agent-runner/package.json`.
