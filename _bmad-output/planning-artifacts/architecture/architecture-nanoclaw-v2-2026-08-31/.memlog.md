- (decision) AD-1 [paradigm]: no new paradigm -- composed extension of the existing layered architecture (host + per-agent-group container, MCP-tool surface, ncl CLI); CAP-1 adds one new container-side MCP tool, CAP-2 adds additive provenance fields to three existing per-domain records plus one new per-group log file mirroring the existing run-log.ts pattern -- no new runtime, no new IPC channel, no new DB table
- (decision) AD-2 [CAP-1 sharing mechanism]: reuse the existing mount-allowlist + ncl groups config add-mount verb as-is for the cross-group grant -- this is already a live, proven precedent (household's people.md mounted read-only into other groups, per CLAUDE.md's isolated-memory pitfall) -- no new grant/approval primitive invented, resolving spec open question 3. add-mount stays approval-gated, hostOnly, operator-configured; CAP-1 does not add self-service dynamic grants
- (decision) AD-3 [CAP-1 discovery filename convention]: the source group's shareable facts live in one fixed, dedicated file -- memory/shared-facts.md, kebab-case, OKF frontmatter matching the existing memory-file convention -- not an arbitrary mounted directory. Prevents one operator mounting a whole memory tree and another mounting a single curated file, which would make a generic query tool impossible to write against
- (decision) AD-4 [CAP-1 query tool]: a new container-side MCP tool, read_shared_context, registered via the existing registerTools([...]) convention (mirrors calendar.ts) in a new mcp-tools/shared-context.ts -- resolves spec open question 1 (MCP tool, not a CLI verb, since this is an agent-runtime read, not an admin config action). Looks under /workspace/extra/<containerPath>/shared-facts.md for every mount the admin has configured via AD-2's add-mount, per the fixed containerPath convention in AD-5
- (decision) AD-5 [CAP-1 containerPath convention]: when an operator runs add-mount to share one group's shared-facts.md with another, the containerPath argument must follow a fixed pattern -- shared/<source-group-folder> -- so read_shared_context can construct /workspace/extra/shared/<source-group-folder>/shared-facts.md deterministically rather than scanning an arbitrary tree. Documented in the CLI verb's own description text
- (decision) AD-6 [CAP-1 no-grant behavior]: read_shared_context returns a clean, explicit not-shared result (never an error, never a silent guess) when no mount exists for the requested group pair -- prevents divergence between an error-throwing implementation and a silent-empty one, both of which would surface wrong to the agent/user
- (decision) AD-7 [CAP-2 provenance shape]: one common minimal shape is reused across all three domains -- { triggeredBy: 'user'|'agent'|'system', requesterSessionId?: string, message?: string, reason?: string, at: ISO-timestamp } -- so a why-query answers uniformly regardless of domain. Prevents tasks/self-mod/documents each inventing an incompatible ad hoc shape
- (decision) AD-8 [CAP-2 tasks]: provenance is stored additively inside the existing messages_in content JSON blob (task rows, kind='task') -- content.provenance using AD-7's shape -- captured at ncl tasks create time from the triggering session/message, alongside the pre-existing prompt/script/originSessionId fields. No schema migration -- content is already a free-form JSON column
- (decision) AD-9 [CAP-2 self-mod]: applyAddCalendar and its self-mod-family siblings (install_packages, add_mcp_server) each append one line to a new per-group durable log, groups/<folder>/self-mod-log.md, at apply time -- mirroring run-log.ts's existing file-per-group markdown log pattern (same convention as task run logs), not a new subsystem type. The shared pending_approvals table itself is left unchanged (still deleted on resolve, per its existing behavior for every other approval-gated action) to avoid widening the blast radius onto action types outside this spec's scope
- (decision) AD-10 [CAP-2 documents]: FillHistoryEntry (documents.ts) gains one additive optional field, provenance, using AD-7's shape -- captured at fillOneDocument/save_document-refresh write time. Existing entries without the field remain valid, per readFillHistory's existing tolerant-reader/backward-compat normalization pattern (already handles pre-kind entries the same way)
- (decision) AD-11 [CAP-2 retrieval, resolves spec open question 2]: on-demand (pull) retrieval only ships in this spec's scope -- list_document_versions is extended to render each entry's provenance when present; tasks' why is answerable via the existing ncl tasks get output (content.provenance surfaced); self-mod's why is answerable by reading self-mod-log.md (AD-9). A periodic push digest is explicitly deferred, not built now -- the source intent doc did not commit to it as a hard requirement
- (decision) AD-12 [verification]: CAP-1 gets a new eval-harness scenario set, eval/scenarios/shared-context.scenarios.ts, following the existing ScenarioSetFactory convention (guest-resolution.scenarios.ts as precedent) and registered in loader.ts's SCENARIO_SETS -- one deterministic case (exact fact match when a grant exists) and one llmJudge case (the agent declines/asks rather than guessing when no grant exists), matching this repo's established verification bar for persona-level claims

- (decision) Fix (rubric-3, critical): Deferred section's 'no host rebuild' claim was factually wrong for this spec -- AD-8 touches src/cli/resources/tasks.ts and AD-9 touches src/modules/self-mod/apply.ts, both real host-side src/** edits needing pnpm run build + service restart per this project's own CLAUDE.md guidance, alongside the container-side fresh-spawn path for AD-4's new MCP tool. Corrected in Deferred
- (decision) Fix (rubric-4 + adversarial-3, high): AD-7's provenance shape had a redundant requesterSessionId that duplicates the pre-existing content.originSessionId (create.ts) with no reconciliation rule, and no way to identify an actual person in a shared-session topology. - (decision) Fix (rubric-5, high): self-mod-log.md had no growth bound, unlike its cited precedents. AD-9 now caps it the same way FillHistoryEntry is capped -- oldest entries trimmed past a fixed count (SELF_MOD_LOG_CAP, mirroring FILL_HISTORY_CAP's role), not unbounded growth

- (decision) Fix (adversarial-2, critical): insertRecurrence (already-shipped) copies content verbatim on every recurrence fire, so content.provenance would silently show stale creation-time context on every fire after the first -- not a bug to route around, a scope clarification: AD-8's provenance field is defined as the series' ORIGINAL creation provenance (why the series exists), by design unchanged across fires. Per-fire 'what happened this run' is a separate, already-solved concern (run-log.ts's existing task_log entries) -- a why-query for one specific firing combines both, never expects content.provenance alone to answer it
- (decision) Fix (adversarial-4): no locking was specified for shared-facts.md or self-mod-log.md. AD-3 (shared-facts.md) and AD-9 (self-mod-log.md, on its host-side writer) both now require the same withLock/atomic-write discipline the sibling document-memory spine's AD-11 already established for exactly this class of shared-file race
