- (decision) AD-1: Calendar access goes through OneCLI Gateway's existing transparent HTTPS proxy -- direct fetch() calls to the real Google Calendar REST API v3 from inside the container. onecli-gateway container skill (already mounted in every container) explicitly lists Google Calendar as a supported app. Binds CAP-1/2/3. Prevents inventing new credential plumbing when this codebase's established mechanism already covers it.
- (decision) AD-2 [ADOPTED, verified via OneCLI SDK d.ts + apps list]: one Google Calendar OAuth connection per OneCLI agent identity, and applyContainerConfig() binds a container's entire outbound network to exactly one identity for its whole lifetime -- no per-request agent switching exists. Therefore every calendar MCP tool call always targets exactly ONE calendar: calendarId=primary under whichever onecli identity the calling container is bound to. The tool itself carries no calendar-selection argument or branching logic. Binds CAP-1/2/3. Prevents building multi-account logic the SDK doesn't actually support.
- (decision) AD-3 [user-confirmed via AskUserQuestion]: Uriel's Google Calendar connects under household's own OneCLI identity (the family scheduling hub). Devorah's Google Calendar connects under her own dm-with-partner identity ('Tina') -- her own OAuth grant, never shared/delegated, matching spec constraint. A chat surface that isn't the target calendar's owner (dm-with-uriel or Tina asking for Uriel's calendar; household or dm-with-uriel asking for Devorah's calendar) relays the request in natural language via the existing send_message MCP tool to the owning agent's wired destination; that agent performs the real calendar action and replies via its own send_message. Reuses two already-existing primitives (per-agent-group OneCLI identity, agent-to-agent messaging) with zero new host-side plumbing -- the alternative (a new host-mediated multi-identity bridge) would mean inventing a new RPC channel for one narrow use case.
- (decision) AD-4: a relayed cross-person calendar action (via send_message) is fire-and-forget/async, not synchronous within the same chat turn -- the target agent wakes on its own poll cycle. Every persona/skill instruction touching this must set that expectation up front ('I'll pass this to Devorah's agent, one sec') rather than imply same-turn completion. Binds CAP-1/CAP-3 (writes); prevents inconsistent latency assumptions across the three personas.
- (decision) AD-5: the requesting user's own sender identity (already available in every chat turn's metadata) determines which calendar an unqualified 'my calendar' refers to -- never defaults to whichever person's calendar happens to be locally connected. Binds CAP-1/2/3 in the shared household chat specifically (multiple real people share that surface). Prevents household's agent silently treating every ambiguous 'my calendar' request as Uriel's even when Devorah is the one asking.

- (decision) AD-8: the gateway's own documented failure contract (401/403/app_not_connected -> connect_url in the response) is the entire not-connected-yet handling -- the tool surfaces that error text back to the agent, which (per onecli-gateway skill's existing instructions) already knows to present the connect link. - (decision) AD-9 (reviewer gate, adversarial finding): send_message carries no marker distinguishing a relayed action-request from a relayed confirmation/result -- a plain-text bounce risks two AD-3-compliant agents re-relaying a 'done' confirmation as if it were a fresh request. - (decision) AD-15 (self-found post-finalize, self-resolved -- automator authority, obvious fix, no genuine ambiguity): AD-6's raw-fetch decision has a real, previously-unchecked TLS-trust gap. The OneCLI SDK's applyContainerConfig (verified: node_modules/.pnpm/@onecli-sh+sdk@2.2.1/.../lib/index.js) sets SSL_CERT_FILE and DENO_CERT env vars for the gateway's injected CA cert, but never NODE_EXTRA_CA_CERTS -- and Bun's fetch() (confirmed via Bun's own docs/issue tracker, web search) only reads NODE_EXTRA_CA_CERTS for custom CA trust, not SSL_CERT_FILE. Nothing in container-runner.ts or the Dockerfile sets NODE_EXTRA_CA_CERTS either. Left as-is, every calendar fetch() call through the gateway's MITM proxy would very likely fail TLS verification (UNABLE_TO_GET_ISSUER_CERT_LOCALLY or equivalent) -- this is exactly why the one existing gateway-proxied precedent (upload-trace.ts) uses curl (which does honor SSL_CERT_FILE) instead of fetch. Fix: at agent-runner startup (before any calendar tool call), set process.env.NODE_EXTRA_CA_CERTS ??= process.env.SSL_CERT_FILE when the latter is present -- a small, defensive, harmless-if-unneeded shim that closes the gap without abandoning AD-6's fetch()-based design or falling back to curl. Binds CAP-1, CAP-2, CAP-3 (every calendar fetch() call). MUST be verified with one real end-to-end fetch() call through the actual running gateway before Story 1.2 is considered done -- not assumed from documentation alone.
- (event) Story cal-1.2 review-gate found and fixed a CRITICAL pre-existing bug: the nanoclaw MCP server subprocess (container/agent-runner/src/index.ts:98, env: {}) never received HTTPS_PROXY/SSL_CERT_FILE/NODE_EXTRA_CA_CERTS at all -- traced through the actual installed @modelcontextprotocol/sdk stdio transport AND the compiled Claude Code binary itself (matching curated env-var allowlist found via strings/grep). This meant AD-1's entire gateway-routing premise, not just AD-15's TLS shim, was non-functional for any MCP tool making an outbound fetch() call -- previously unexercised since no prior MCP tool made outbound network calls. Fixed by changing that line to env: { ...process.env } -- a first-party trusted MCP server, so full env inheritance is the correct fix, not a security regression. This is the most significant single finding across both epics reviewed in this session; logged here since it's a systemic gap the architecture-level reviewer gate did not catch (none of the 3 spine-review lenses traced down to actual MCP stdio-transport spawn semantics).
