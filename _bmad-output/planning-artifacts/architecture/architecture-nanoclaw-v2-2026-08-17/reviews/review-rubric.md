# Rubric Walk — Architecture Spine: Google Calendar Read/Write

Reviewed: `ARCHITECTURE-SPINE.md` + `.memlog.md` (this dir), driving spec `_bmad-output/specs/spec-google-calendar/SPEC.md`, against the real repo at `/Users/uriel/Projects/nanoclaw-v2`.

**Verdict: CONDITIONAL PASS.** The spine's SDK/gateway/convention claims all check out against the real code, and it correctly composes existing primitives instead of inventing new plumbing — but it leaves two genuinely divergence-prone dimensions (event timezone construction; cross-person-relay disambiguation) completely silent, and one existing-persona contradiction risk unaddressed, that stories built from this spine could easily land incompatibly or in direct conflict with already-shipped agent behavior.

---

## Findings

### 1. [HIGH] Event timezone handling is entirely unaddressed
No AD, Consistency Convention, or Deferred entry says how `create_calendar_event`/`update_calendar_event` turn a chat request like "Thursday at 3pm" into a Google Calendar `dateTime`+`timeZone` pair. This codebase already has a load-bearing, documented convention for exactly this problem — `resolveGroupTimezone` (`src/container-config.ts:56`) sets the container's `TZ` env at spawn, and `container/agent-runner/src/timezone.ts` mirrors it host-side (`process.env.TZ` / `Intl.DateTimeFormat().resolvedOptions().timeZone` fallback) — but the spine never ties AD-6's `fetch()` calls to it. Deferred's only adjacent entry ("Exact `fetch()` request/response typing... implementation detail, not an invariant") is the wrong bucket for this: it's not typing, it's semantic correctness. Two independently-built tools (create vs. update) could easily diverge — one naively uses UTC/no `timeZone` field, the other uses the group's local TZ — producing events silently created at the wrong hour, which is exactly the "diverge incompatibly" failure the Deferred section is supposed to rule out.

**Recommendation:** add an AD pinning event `dateTime`/`timeZone` construction to the existing `resolveGroupTimezone`/container `TZ` convention (or an explicit, single source of truth), binding CAP-1 and CAP-3.

### 2. [HIGH] AD-7's disambiguation precedent doesn't survive AD-3's cross-person relay
AD-7 justifies its "numbered list, wait for a pick" rule by citing `spec-document-memory`'s CAP-2/CAP-3 precedent. Verified in `container/agent-runner/src/mcp-tools/documents.ts` (`kind: 'candidates'` around line 1027-1035): that precedent is a **same-turn, same-container** loop — the tool returns candidates, the agent presents them, waits, and re-calls the *same* tool in the *same* session.

AD-3 makes calendar access single-owner-per-identity: a household user asking to update Devorah's ambiguous event can't be disambiguated by household's own container at all (its outbound network, per AD-2/`applyContainerConfig`, is bound only to household's own OneCLI identity — it cannot even call `list_calendar_events` against Devorah's calendar to build a candidate list). The disambiguation would have to happen inside Tina's (`dm-with-partner`'s) turn, replying to Devorah's own DM — not to the original household requester who asked the question and needs to make the pick. The spine never resolves this multi-hop case (relay → disambiguate → relay the pick back), and it isn't even named in Deferred. This is a real fork two independent builders could resolve incompatibly (or one could simply not notice the gap and let the owning agent silently guess, violating the spec's own "never guess" constraint).

**Recommendation:** either explicitly restrict AD-7's guarantee to same-surface requests and add an AD for the cross-relay case (e.g., the owning agent relays the candidate list back through `send_message` to the original requester's destination, and the pick flows back the same way), or note it as an open question — not silence.

### 3. [HIGH] Existing persona text already generalizes over AD-8's connect-link requirement
CLAUDE.md's own pitfall log (in this repo) already documents this exact failure mode: *"A per-group `instructions.prepend.md` can silently override or shadow a newly-shipped capability... the agent trusts its older, more specific-sounding persona text over a capability it was just told about."* This spine trips over it without noticing:

- `groups/household/instructions.prepend.md:43`: *"Data sources for second-brain are wired by the operator (Uriel) directly... never through you, never through OneCLI's dashboard. If either person asks whether something is connected, answer honestly... **don't hand out a link, don't walk anyone through connecting it yourself, and don't imply you're able to.**"*
- `groups/dm-with-uriel/instructions.prepend.md:120`: *"...never through you, never through OneCLI's dashboard, even for his own account... point to second-brain's own auth CLI rather than OneCLI — **don't hand out a OneCLI connect link.**"*

Both were written about second-brain's separate per-tenant OAuth flow, but the wording is broad ("If either person asks whether something is connected") and sits right next to calendar-flavored language in the same files (`household:25` "inbox/calendar review", `dm-with-partner:37` "calendar... may get wired into `partner.db` later"). AD-8 requires the *opposite* behavior for the new tool: surface the gateway's `connect_url` and let the agent present it, per the `onecli-gateway` skill's own instructions (verified: `container/skills/onecli-gateway/SKILL.md` — "Show the user a connect link. Use the `connect_url`..."). Nothing in the Structural Seed's `container/skills/calendar/SKILL.md` plan flags that this needs to be explicitly disambiguated from the adjacent second-brain OAuth language already in these personas. Left as-is, an agent applying the older, more specific-sounding persona rule to the new capability produces exactly the opaque-decline behavior the spec explicitly forbids ("never... fails with an opaque error").

**Recommendation:** add a line to the calendar skill (or an AD) explicitly distinguishing "second-brain OAuth" (never disclose a link) from "OneCLI Google Calendar app connection" (always disclose `connect_url` per AD-8) — the two now coexist in the same personas and are easy to conflate.

### 4. [MEDIUM] AD-6's core mechanism (`fetch()` + `HTTPS_PROXY`) has no in-repo positive precedent and no memlog version-check
AD-6/Stack commits to Bun's native `fetch()` reaching Google Calendar through the container's injected `HTTPS_PROXY`, with no client library. The *only* existing in-repo precedent for a gateway-proxied outbound call, `container/agent-runner/src/upload-trace.ts:15-17` ("Auth is the OneCLI gateway's job: curl goes out through the injected HTTPS_PROXY"), uses `curl` via `spawnSync` — a different network stack from Bun's native `fetch()`. `docs/SECURITY.md:129` is explicit that egress lockdown exists precisely *because* "`HTTPS_PROXY` env var only redirects *proxy-aware* clients." Whether Bun's native `fetch()` is itself proxy-env-aware out of the box is the single most load-bearing unverified assumption in the whole spine (if it isn't, AD-1 and AD-6 don't work at all, egress lockdown gives it nowhere to go, and the fix is to fall back to the curl-subprocess pattern that already has a working precedent) — yet the memlog's version-check entries cover Google Calendar API v3 and `@onecli-sh/sdk@2.2.1` but never this.

**Recommendation:** add a version-check memlog entry confirming Bun's `fetch()` honors `HTTPS_PROXY`/`HTTP_PROXY` (Bun does document this, but it should be confirmed the way AD-2 confirmed the SDK claim — by reading the actual behavior/docs — rather than left implicit), or fold the curl-subprocess fallback into AD-6's `[ASSUMPTION]` explicitly.

### 5. [LOW] New calendar skill will auto-mount into every group, not just the three real surfaces
Verified: all 4 existing `container_configs` rows (including the `_ping-test` throwaway group) have `skills: 'all'`, and `selectedSkillNames()` (`src/container-runner.ts:532-544`) recomputes `'all'` from every directory under `container/skills/` — so the new `container/skills/calendar/` will mount into every container regardless of whether that agent group has any Google Calendar OAuth grant. AD-8 makes this functionally harmless (gateway 401/403 handled gracefully), but the Structural Seed doesn't note the scope leak, and any future non-calendar group inherits calendar-shaped instructions for no reason.
