- (decision) Delivery safety: a dedicated eval agent group (not a normal production group, not a reused ad-hoc leftover) with ZERO destinations configured. Binds CAP-1/CAP-4. Prevents: an eval scenario's own <message to="X"> reply resolving to a real destination and delivering to a live Telegram/WhatsApp/etc chat, since this repo is the live production host with its real delivery pipeline always running. Structural guarantee (nothing to resolve to), not a 'be careful' convention. Considered and rejected: reusing the leftover _ping-test/Terminal Agent group (unverified destination config, not built with this in mind) and a fully isolated DB copy per run (correct but heavier setup than needed given the destinations-based guarantee already closes the real risk).
- (decision) In-process host module reuse: eval/ is a host-side TypeScript package that imports src/container-runner.ts (wakeContainer), src/session-manager.ts (writeSessionMessage, openOutboundDb), and src/db/sessions.ts (createSession) directly — the exact same functions the real host process calls, not a reimplementation or a network-boundary call. Runs as its own script/process sharing the live data/v2.db via the same better-sqlite3 connection pattern the host already uses. Binds CAP-1 (real container path). Prevents: a parallel spawn implementation drifting from production behavior over time, and prevents an SDK-only shortcut that SPEC.md's own Constraints section already ruled out.
- (decision) Judge credentials: the LLM-judge call runs through its own lightweight container spawn, reusing the exact same OneCLI credential-injection path every other Claude call in this codebase uses — the host process is never given direct Claude API access. Binds CAP-3. Prevents: a new, unprecedented credential-access surface on the host process, deviating from the established 'only containers call Claude, credentials never touch env vars or host code' security model (onecli-gateway skill, container-runner.ts ensureAgent).
- (decision) Report format/storage: each run writes a JSON report (per-scenario id, verdict, evidence, timestamps) under eval/reports/<run-id>/report.json, plus a human-readable console summary printed at the end of the run. [ADOPTED-by-inference] matches this project's own convention of JSON DB-adjacent artifacts + human-readable CLI/log output (e.g. ncl's own --json flag pattern, sprint_status.py's JSON responses).
- (event) Reviewer gate ran: rubric walker + version-verification lens + adversarial-incompatibility lens, 3 parallel subagents. Versions: PASS, clean. Rubric + adversarial: NOT ready to build from as-is — 3 critical, 4 high, 2 medium findings, reviews saved under reviews/review-{rubric,versions,adversarial}.md.
- (decision) AD-1 REVISED (adversarial finding, critical): zero-destinations alone does not close the delivery-safety guarantee -- delivery.ts's origin-chat reply path bypasses the destinations table entirely (it's how every normal conversation reply already works, no destination lookup needed). Real fix: eval sessions get messaging_group_id=NULL (no origin chat to bypass into), reusing the existing system:-thread convention already used for scheduled tasks (rubric finding) for thread_id. Zero-destinations kept as a second layer (blocks the cross-group routing path), not the sole guarantee.
- (decision) New AD (rubric finding, critical): host-sweep.ts and the eval CLI are separate OS processes with disjoint in-memory state (isContainerRunning/activeContainers is process-local to whichever process calls it). The always-live host service's own 60s sweep will see an eval-spawned container as not-running and duplicate-spawn it, corrupting in-flight scenario capture. Fix: eval sessions get a DB-level exclusion marker host-sweep.ts's global session queries (getRunningSessions/getActiveSessions callers) explicitly skip -- a real host-side code change (host-sweep.ts), not just new eval/ code. This is the single biggest scope change from the original spine: eval-harness isn't purely additive, it touches existing host session-lifecycle code.
- (decision) New AD (rubric finding, critical): CAP-4's calendar isolation had no structural guarantee -- the built-in uriel->primary (real household calendar) is unconditionally resolvable by every group's calendar tool, including the eval group, since resolveCalendarIds() always merges the built-in with the registry. Real fix, reusing an EXISTING mechanism rather than inventing one: the eval agent group's calendar_registry gets a name-override entry {name: uriel, calendarId: <eval-test-calendar-id>} -- calendar.ts's config-registry-wins-on-collision behavior (Story 2.3, AD-18) already makes a registry entry override a built-in name. Same trick applies to any other built-in/registry name a scenario might reference. Zero new calendar.ts code needed -- only the eval setup step's own registry writes.
- (decision) New AD (adversarial finding, high): AD-3's judge container spawn falls outside the original AD-1's literal 'every scenario run's container' scope -- a second, ungoverned path to a real chat send if the judge doesn't independently get the same isolation. Fix: the judge call spawns under its OWN dedicated agent group (same treatment as the scenario group: messaging_group_id=NULL, zero destinations, calendar-registry override N/A since judge doesn't touch calendars) -- not the scenario's own group, so a judge bug can't touch scenario state either.
- (decision) New AD (adversarial finding, high): concurrent scenario runs (or a run overlapping the standalone sweep) race on the same eval agent group's shared RW-mounted groupDir (memory/CLAUDE.md) -- container-runner.ts mounts this per-group, shared by every session under that group. Fix: reuse the existing project precedent for this exact class of problem -- an mtime-heuristic stale-lock file (already used for document-memory locking elsewhere in this codebase) under the eval group's workspace, acquired by cli.ts before any run/sweep starts, released on exit; a second concurrent invocation fails loud with a clear message rather than racing silently.
- (constraint) Operational envelope (rubric finding, medium): eval runs are meant to happen WHILE the live host service keeps running (this repo IS production, the service is never stopped for a test run) -- every AD above is written under that assumption, not 'stop the host first.' Explicitly stated now rather than left silent.
- (decision) Fix (adversarial finding, critical): scenario-format.md's own worked example hardcoded the REAL household group's UUID as agentGroupId, directly contradicting the dedicated-eval-group requirement. Corrected to reference the dedicated eval agent group (created by eval setup, not a real production group) instead.
- (decision) Follow-on gap caught while fixing scenario-format.md's example (self-caught, not from a reviewer pass): the dedicated eval agent group (AD-1) has no people.md by default -- it's a brand-new group, not household. The guest-resolution scenario's whole premise (resolve Devorah's real email) needs it. Fix: setup.ts read-only-mounts household's real people.md into the eval group, reusing the EXACT existing mechanism from this session's own live fix for Yulanda/Tina (ncl groups config add-mount + mount-security allowlist entry) -- not new code, same pattern AD-7 already established for calendar overrides: reuse, don't invent.
