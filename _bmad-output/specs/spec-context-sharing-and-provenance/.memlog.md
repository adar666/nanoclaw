- (note) Source: brainstorm-intent.md (2026-08-31 brainstorm session), fully absorbed -- both directions the user confirmed to carry forward
- (decision) One spec, two capabilities -- shared-fact resolution and provenance/receipts are separate mechanisms but ship as one initiative (same trust/transparency theme, same intent doc, same brainstorm)
- (capability) CAP-1 intent: an agent group can query facts explicitly permitted to share from another agent group's memory, read-only, without a full memory merge and without breaking default isolation
- (capability) CAP-1 success: a fact recorded in group A's memory that group B is permitted to see is retrievable and usable by group B's agent within its own session, with no user having supplied it to group B directly -- verified via a real eval-harness scenario, matching this repo's existing bar for persona-level behavioral claims (project-context.md: industry-standard rigor, not household-minimal)
- (capability) CAP-2 intent: every automated system action (scheduled task creation/firing, self-mod change, document write) records a retrievable one-line trigger+requester at creation time, answerable on demand
- (capability) CAP-2 success: for any task, self-mod change, or document write made by the system, the user can ask why it happened and get back the recorded trigger+requester, sourced from data captured at creation time, not reconstructed after the fact
- (constraint) CAP-1 permission gate reuses the existing mount-allowlist mechanism (src/modules/mount-security) -- no new trust boundary invented; a group's own memory stays the default, sharing is explicit opt-in per source group, matching the isolation-model's existing three levels
- (constraint) CAP-1 is read-only and non-bidirectional by default -- a query surface, not a sync mechanism; no write-back into another group's memory
- (constraint) CAP-2 reuses existing structures (task metadata, self-mod approval log, memory provenance pattern) -- no new storage subsystem or event bus
- (constraint) Both capabilities route through existing IO surfaces only -- the two-DB session split and existing MCP-tool/CLI boundaries; no new IPC channel between host and container or between containers
- (constraint) Per project-context.md: build to the industry-standard bar already set by this repo's other epics (real test coverage on both host and container trees, eval-harness scenario coverage for the persona-level CAP-1 claim) -- not scoped down to household-minimal
- (decision) Non-goal: not a full bidirectional memory merge or real-time sync across agent groups -- CAP-1 stays a scoped, explicit, read-only query
- (decision) Non-goal: not retroactive -- CAP-2 does not backfill provenance for tasks/changes made before this ships
- (decision) Non-goal: not a new generic pub/sub or event bus between agent groups
- (decision) Non-goal: trust-via-visible-uncertainty (ask-don't-guess as a cross-cutting persona rule), generalizing the idempotency-guard/undo patterns system-wide, and persona-tuned risk profiles are explicitly out of scope for this spec -- named in the source intent doc as deliberately deferred, not dropped
- (assumption) Assumed CAP-1's 'family facts' shape (durable facts: birthdays, sizes, preferences) is the right first scope, distinct from full conversational memory or calendar/documents -- per the intent doc's narrowed first-cut shape
- (assumption) Assumed CAP-2's digest surfacing layer (periodic recap of what's being automated) is in scope as part of 'answerable on demand' rather than a separate capability -- the intent doc frames it as the natural surfacing layer for the same provenance data, not a distinct mechanism
- (question) Open: which specific query interface for CAP-1 -- a new MCP tool (like calendar/documents), an ncl CLI verb, or both -- left for architecture to decide against existing tool-surface conventions
- (question) Open: for CAP-2, whether the digest is push (proactive periodic message) or pull (on-demand query) by default, or both -- intent doc mentions monthly + first-run push framing but doesn't commit to it as a hard requirement
- (question) Open: CAP-1's cross-group permission needs an admin-configurable grant (which group can see which other group's facts) -- unclear whether this reuses ncl groups config add-mount as-is or needs a lighter-weight verb purpose-built for fact-sharing rather than raw directory mounts
