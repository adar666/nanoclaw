- (direction) User: sends Word/PDF, asks to save to memory -> both file and its extracted info should persist in agent memory; also wants to request edits ('fill row X with value Y') and get the updated document back.
- (note) Grounding (Explore agent): inbound attachments already land at data/v2-sessions/<group>/<session>/inbox/<msgId>/<filename> (session-manager.ts extractAttachmentFiles), visible to the container agent as /workspace/inbox/<msgId>/<filename>. No new inbound plumbing needed to receive the file.
- (note) Grounding: group memory is file-based at groups/<folder>/memory/ (host) = /workspace/agent/memory/ (container), documented in docs/memory.md, OKF-frontmatter convention, index.md always injected as Core Memory. No agent_groups DB memory field -- this is the natural home for saved-document records.
- (note) Grounding: outbound file delivery already works end-to-end via send_file MCP tool (container/agent-runner/src/mcp-tools/core.ts) -> outbox/<msgId>/<filename> -> messages_out content.files -> delivery.ts readOutboxFiles -> channel adapter. No new outbound plumbing needed to return an edited file.
- (note) Grounding: no docx/pdf read or write library exists anywhere in the container today (checked container/agent-runner/package.json, Dockerfile, container/skills/*). Must be added as a new dependency; container/agent-runner is Bun, adding a dep needs bun install + bun.lock commit + ./container/build.sh + service restart per CLAUDE.md gotchas.
- (note) Grounding: closest structural analog for a new document skill is container/skills/audio-report/SKILL.md -- reads an inbox-attachment path tag, transforms, writes new output file, calls send_file. A new docx/pdf skill should follow this same shape.
- (decision) 'Row/field to fill' is ambiguous by design and must stay flexible: user confirmed it can be a Word table row, a PDF AcroForm field, or an arbitrary free-text line/number depending on the file -- the feature must handle all three, not pick one.
- (decision) PDF edit strategy fixed by user: never parse/reflow PDF text to edit in place. Instead overlay new text on top of the existing PDF page (stamp/draw text at a position) and save as a new PDF -- works uniformly for form-field PDFs and plain/scanned PDFs alike, avoids reflow risk entirely.
- (decision) Memory depth confirmed: saving a document to memory means BOTH the raw file/full extracted text AND a summary entry in memory/index.md (OKF concept file) pointing to it, not just a full-text dump -- so future recall is a fast index lookup, not a full-text re-scan every time.
- (decision) Container image rebuild cost (adding a docx/pdf library, e.g. python-docx-equivalent for Bun/JS, plus a PDF overlay lib) accepted by user as a real constraint of this spec, not deferred to a separate epic.
- (capability) CAP-1 Save document to memory: user sends a Word/PDF attachment and asks to remember/save it -> agent stores the file plus its extracted text content in group memory, with a summary entry in memory/index.md. Success: a later, fresh conversation can ask about the document's content and get a correct answer without the file being resent.
- (capability) CAP-2 Recall saved document content: user asks about a previously saved document at any later time -> agent answers from the memory/index.md summary and stored extracted text. Success: a query referencing a document saved in a prior session returns content-accurate answers.
- (capability) CAP-3 Fill a value into a saved document and return it: user names a target (table row / form field / text line, per file type) plus a value, in a previously-saved document -> agent produces an updated copy with the value applied and delivers it back in chat via send_file. Success: for Word, the named table row's cell contains the new value and the rest of the document is byte-for-byte structurally unchanged; for PDF, a new PDF is returned with the value overlaid/stamped at the correct location and the original page content otherwise unchanged.
- (constraint) PDF value-filling must use an overlay/stamp technique (draw new text on top of the existing page, save as new PDF) -- never parse-and-reflow PDF text in place. Rules out any PDF library approach that requires re-typesetting or content-stream text replacement.
- (constraint) Row/field targeting must handle three distinct mechanisms depending on file type -- Word table row, PDF AcroForm field, or PDF overlay-by-position for plain/scanned PDFs -- selected automatically from the file, not chosen by the user. Rules out a single-technique implementation.
- (constraint) Saved documents and their extracted content live under the requesting agent group's memory/ tree (file + memory/index.md entry per docs/memory.md's OKF convention) -- not the separate second-brain media-ingestion pipeline (src/media-ingestion.ts), which is a different tenant-scoped system for specific DM groups only.
- (constraint) Editing must return the updated file through the existing send_file MCP tool / outbox delivery path (container/agent-runner/src/mcp-tools/core.ts) -- no new outbound delivery mechanism.
- (constraint) No docx/pdf read or write library exists in the container today -- shipping this feature requires adding a new dependency to container/agent-runner/package.json (bun install + bun.lock commit) and a container image rebuild (./container/build.sh + service restart). Accepted as an in-scope constraint of this spec, not deferred.
- (non-goal) Restructuring, reformatting, or redesigning document layout -- only single-value fill-ins into an existing row/field/line, never new sections, styling changes, or content beyond the requested value.
- (non-goal) Concurrent/collaborative multi-user editing of the same saved document, or version-conflict resolution across overlapping edit requests.
- (non-goal) File types other than Word (.docx) and PDF (.pdf) -- other formats (xlsx, pptx, images, plain text) are out of scope for this spec.
- (non-goal) Full reflow / re-typeset PDF text editing -- explicitly excluded in favor of the overlay approach (see PDF edit strategy constraint).
- (assumption) Assumed memory is scoped per agent group (shared across all users of that group's DM/chat), matching existing memory/index.md semantics -- not per individual user within a group. No signal in the input suggested per-user isolation.
- (assumption) Assumed 'saved' documents are referenced by the agent picking up on filename/topic from conversation context (same as any other memory item), not by a formal document-ID the user must quote.
- (question) Scanned/image-only PDFs: the overlay-write technique works regardless (drawing on top of any PDF page), but CAP-1's 'extracted content in memory' requires readable text -- no OCR capability exists in this repo. Should scanned PDFs get file-only memory (no extracted text, findable by filename only), or is OCR in scope for CAP-1?
- (question) Disambiguation: when multiple documents are saved in a group's memory and the user says 'fill row 3 with X' without naming a file, how does the agent choose which document -- most recently saved, most recently discussed, or must it always ask?
- (question) PDF overlay positioning for plain (non-form) PDFs: locating where 'row X' sits on the page to draw the value at correct coordinates needs some text-position/layout detection. Is approximate agent-driven placement (agent reads extracted text with positions, estimates coordinates) acceptable, or does this need a more deterministic table/line-detection step?
- (question) Word 'row X' numbering convention when a document has multiple tables: is X a global row index across all tables in document order, or must the user also identify which table? Confirmed the target can be a table row, but the addressing scheme within multi-table documents is unresolved.

- (decision) OQ resolved (scanned PDFs): user asked for best practice, researched (2026 OCR-vs-vision-LLM benchmarks). Chosen approach: hybrid, no new OCR engine dependency -- PDFs with a text layer get direct text extraction as before; PDFs with no text layer (scanned/image-only) are rendered to page images and read directly by the multimodal agent itself, since the agent (Claude) is already vision-capable and the container already renders pages/screenshots elsewhere (agent-browser). Avoids adding a heavyweight OCR engine (e.g. Tesseract) purely for this.
- (decision) OQ resolved (multi-document disambiguation): when the target saved document is ambiguous (user didn't name one, or the name matches more than one), the agent presents a numbered list of candidate documents from memory and the user replies with a number to pick. Applies to both CAP-2 recall and CAP-3 edit-and-return.
- (decision) OQ resolved (PDF overlay positioning): researched. Hybrid, matching the OCR decision -- when the PDF has a text layer, use a PDF text-extraction library that returns per-text-item coordinates/bounding boxes to locate the target line precisely. When there is no text layer (scanned), the agent visually estimates the target region from the rendered page image, and that estimate is converted into PDF point-coordinate space (page is points, y-axis runs bottom-up) using the known page dimensions and render scale factor.
- (decision) OQ resolved (Word multi-table addressing): row targeting in a multi-table Word document is addressed as a (table number, row number) pair -- the user names both, not a single global row index across all tables.
