topic: Agent evaluation harness — real test infrastructure to verify persona-level agent behavior actually holds, starting with calendar-skill guest-email resolution, designed to generalize
updated: 2026-08-19T23:18
---

- (constraint) Project-wide standing directive (project-context.md, 2026-08-19): treat this as industry-standard eval infrastructure (promptfoo / LangSmith evals / golden-transcript+LLM-judge spirit), not a household-scoped shortcut — real design decisions get made deliberately.
- (direction) Starting case: calendar SKILL.md's guest-email-resolution claim (proactive resolve by name, ask on ambiguity, never guess) — currently untestable, flagged in deferred-work.md. Harness should generalize to other persona-level behavioral claims across the project (e.g. AD-5 sender-identity resolution), not be calendar-specific.
- (decision) Execution mode: real container, full stack — spin up the real per-agent-group Docker container (production path), write a real inbound message, poll outbound.db for the response. Exercises real MCP tools, real SKILL.md composition, real container lifecycle. Prevents: a fast SDK-only harness that passes while the real container/DB integration is broken.
- (decision) Judging: hybrid — deterministic assertions where a scenario has a single checkable fact (email sent, tool call made, text present/absent); LLM-judge (second Claude call against a written rubric) for qualitative behavioral claims (e.g. "asked the user instead of guessing"). Prevents: forcing every claim into a brittle exact-match, or trusting an LLM judge for facts that don't need one.
- (decision) Cadence: on-demand only for v1 — a script run manually before/after a persona-affecting change or periodically by hand. No CI integration, no scheduled cost. Matches project scale now; CI/scheduled graduation is a real future option, not built now. Prevents: committing to per-PR real-API cost before the harness has proven its value.
- (decision) Test isolation: dedicated test calendar registry entry (a real but throwaway Google Calendar, registered via add_calendar) — real API calls, real side effects, isolated from actual household/personal calendars. Scenarios clean up their own test events after running. Prevents: eval runs polluting Uriel's real calendar, and prevents the false confidence of a fully-mocked fetch layer that never touches the real Google API.
- (decision) V1 scope: narrow, designed to generalize. Build enough structure (scenario format, runner, judge) to cover guest-resolution scenarios well, but keep the scenario format and runner interface generic (not calendar-specific field names) so a second behavioral claim (e.g. AD-5 sender-identity resolution) can reuse the same runner without a rewrite. Prevents: over-building a speculative taxonomy before a second real use case exists to validate the abstraction against.
- (decision) Location: new top-level eval/ directory, parallel to src/ and container/ — its own package with a CLI entry point (e.g. pnpm eval run guest-resolution). Reflects that this is neither host nor container code — it orchestrates both (spins up real containers, talks to session DBs, calls the judge). Prevents: awkwardly wedging a multi-file orchestration package into scripts/, which is single-script-oriented by convention.
- (capability) CAP-1: run a scenario against the real agent and get a pass/fail verdict — spin up the real per-agent-group container, send a scripted message, capture the transcript/outcome. success: a scenario run produces a pass/fail with evidence (the email actually used, or that the agent asked instead).
- (capability) CAP-2: deterministic assertions for checkable facts — a scenario with one correct answer (right email used, or nothing sent) is checked exactly, no LLM involved. success: a deterministic scenario's verdict is fully reproducible given the same transcript.
- (capability) CAP-3: LLM-judge for qualitative claims — a scenario like "asked the user instead of guessing" is graded by a second Claude call against a written rubric. success: the judge's verdict AND its reasoning are both recorded, not just a boolean.
- (capability) CAP-4: isolated test calendar — scenario runs never touch real household/personal calendars, only a dedicated eval-test calendar registered via add_calendar. success: every event an eval run creates/attempts lands only on the eval-test calendar, and gets cleaned up (or the run reports a cleanup failure explicitly, never silently).
- (capability) CAP-5: generic scenario/runner interface — the scenario format and runner aren't calendar-specific. success: adding a second scenario domain (e.g. sender-identity resolution) requires zero runner-code changes, only new scenario definitions + judge rubric.
- (capability) CAP-6: on-demand CLI invocation — a human runs the harness manually (e.g. pnpm eval run guest-resolution); no CI/schedule wiring in v1. success: running the command produces a saved report (per-scenario verdict + evidence) with no CI or cron dependency.
- (constraint) Every scenario run costs real Claude API tokens (real container, real model calls) — bounds run frequency and reinforces on-demand-only cadence for v1, not a cheap thing to run casually or in a loop.
- (constraint) Scenario runs must never write to Uriel's real household/personal Google Calendars — only the dedicated eval-test calendar.
- (non-goal) CI integration and scheduled/nightly runs are explicit non-goals for v1 — on-demand only, revisit once the harness has proven its value.
- (non-goal) A full generic taxonomy covering every persona-level claim in the project (beyond guest-resolution) is explicitly out of scope for v1 — the runner interface stays generic, but only one scenario domain ships now.
- (non-goal) Multi-turn conversation-drift / long-session behavioral testing is out of scope — v1 scenarios are single-exchange (one scripted request, one real container spawn, one verdict), not simulating a long conversation history.
- (decision) Success signal: running the harness against the guest-resolution scenario set produces genuine per-scenario pass/fail evidence (not just 'ran without crashing') for the real behavioral claims already live-tested ad hoc this session (e.g. 'תוסיף את דבורה כאורחת' -> correct email; ambiguous name -> agent asks, doesn't guess). Concretely demonstrates the gap this spec exists to close: a persona claim that was previously only checked by a human eyeballing one live Telegram exchange is now independently re-checkable on demand.
