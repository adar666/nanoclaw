- (capability) CAP-1: create a new event (title, description, location, start/end time, guest emails) on a named calendar (Uriel's or Devorah's), from a natural-language chat request. Success: agent creates a real Google Calendar event with the requested details on the correct calendar and confirms back with the event's details/link.
- (capability) CAP-2: read/query a named calendar's contents for a time range or a specific question (what's on today/tomorrow/this week, when is X). Success: agent answers from real, current calendar data, not memory/guesswork.
- (capability) CAP-3: update an already-created event's details (time/location/guests/description) that the agent can identify unambiguously on a named calendar; if the reference is ambiguous, present a numbered candidate list (same disambiguation precedent as spec-document-memory's CAP-2) and wait for a pick rather than guessing. Success: the named event's changed field(s) reflect the new value on the real calendar, everything else about the event unchanged.
- (constraint) Google Calendar only (user-confirmed via AskUserQuestion), not Outlook/other providers.
- (constraint) Two named calendars only: Uriel's and Devorah's. Each is authenticated with its own independent OAuth grant through the OneCLI Agent Vault (user-confirmed: Devorah connects her own, no shared/delegated access through Uriel's grant).
- (constraint) Credentials are never passed through chat, code, or env vars -- routed exclusively through the OneCLI Gateway proxy, same pattern as every other credentialed action in this codebase (onecli-gateway container skill).
- (constraint) If a request targets a calendar whose OAuth isn't connected yet (most likely Devorah's, initially), the tool declines clearly with instructions to connect it via OneCLI -- never silently falls back to the other calendar or fails with an opaque error.
- (constraint) The target calendar (Uriel's vs Devorah's) is always an explicit argument/selection -- never inferred/guessed when a request is ambiguous about whose calendar it means; the agent asks.
- (constraint) New MCP tool(s) live under container/agent-runner/src/mcp-tools/, registered via the existing McpToolDefinition + registerTools() convention -- same mechanism as the document-memory tools.
- (constraint) All calendar writes (create/update) are triggered by an explicit user chat instruction in the same turn -- no autonomous/background/scheduled calendar writes without a direct request.
- (constraint) Exact Google Calendar client library (Node/Bun-compatible) is not pinned here -- deferred to the architecture stage's stack research, mirroring how spec-document-memory left library versions to its own architecture spine.
- (non-goal) Deleting/cancelling an event is out of scope for v1 -- a separate, higher-stakes destructive action than create/update; revisit if requested.
- (non-goal) Recurring-event creation (e.g. 'every Thursday') is out of scope for v1 -- single-occurrence events only; revisit if requested.
- (non-goal) Calendars other than Uriel's and Devorah's (a shared/family calendar, an invited guest's own calendar) are out of scope.
- (non-goal) Free-busy conflict detection / scheduling-suggestion logic beyond what's explicitly asked is out of scope for v1.
- (assumption) Which agent group(s)/wiring this tool is exposed through (household, dm-with-uriel, a new per-person grouping) is an architecture-stage decision, not resolved here.
- (assumption) 'Guests' means attendee email addresses added to the event; the agent may already know some people's emails from existing household memory (groups/household/memory/household/people.md) and can ask when it doesn't.
- (question) Exact Google Calendar client library/version -- open, resolved at architecture stage.
- (question) Whether an unresolvable guest email blocks event creation or the agent asks and proceeds without it -- open, resolved at build stage.

- (constraint) CORRECTION (2026-08-17, architecture-stage discovery): the original constraint 'each authenticates with its own independent OAuth grant... no shared/delegated access' was wrong at the OAuth-connection layer -- OneCLI's Google Calendar app is one connection per project, not per identity (live-verified). The actual, working mechanism is the opposite of what was stated: Devorah shares her Google Calendar with the one connected account (Google Calendar's own native sharing, granting 'Make changes to events' access) -- this IS delegated access, by design, and is how CAP-1/2/3 actually reach her calendar. Both people's calendars remain two separate, independently-owned Google Calendars (that part of the constraint's intent holds); only the OAuth-connection mechanism description was wrong.
